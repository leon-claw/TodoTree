# 新项目初始化

把新项目从需求梳理推进到可运行的 Gemini 初始模板，并补齐仓库指引、设计规范和结构图。首个版本保持最小、可运行。

## 流程

1. **检查项目并理解需求。** 查看当前目录、现有文件和 `AGENTS.md`，保留已有内容。将新项目视为架构型任务，使用 `superpowers:brainstorming` 逐个询问项目目的、目标用户、首版必需能力、平台、限制和成功标准。明确询问用户希望的设计风格，以及是否有参考网站、产品或截图；如果用户尚未确定，可根据项目定位给出 2–3 个风格方向供选择。每次只问一个重点问题，不擅自扩展需求。

   如果当前环境没有 brainstorming skill，从 [obra/superpowers](https://github.com/obra/superpowers) 获取完整技能套件，并安装到当前项目的 `.agents/skills/`。先把官方仓库取到临时目录，再将 `skills/` 下每个完整 skill 目录复制到项目中；保留配套文件和已有 skill，遇到同名冲突时不要覆盖。安装好后继续 brainstorming。

2. **生成 Gemini 提示词。** 需求明确后，生成一份可直接复制到 [Google AI Studio](https://aistudio.google.com/) 的中文提示词。写清项目目的、主要用户、必要流程和页面、目标平台、已知的数据与持久化需求、用户选定的设计风格及参考，以及明确的非目标。要求 Gemini 只生成满足需求的最小端到端可运行模板，不添加未要求的功能、臆测性抽象、演示内容、不必要依赖或无关配置，也不要替用户补造未确认的需求。

   展示提示词，并请用户亲自到 AI Studio 生成模板后放入当前项目。**在此暂停。** 只有用户确认文件已放入项目或提供了文件路径后才能继续。在等待期间不要自行搭建、安装依赖或改写项目文件。

3. **审查并中性化 Gemini 模板。** 完整检查用户放入的目录、源码、依赖、脚本、运行配置和文档，并逐项对照已确认的需求。找出 AI Studio/Gemini 平台专用的包装层、运行时假设、部署适配、无关 SDK、示例代码和配置。删除与产品需求无关的平台代码；需要保留的功能改用所选框架和运行环境中的标准、中性实现，同时清理对应的依赖、导入、脚本、环境变量示例和文档引用。若产品本身明确需要 Gemini API，保留实现该功能所必需的集成，只移除 AI Studio 专属的多余层。不要因清理而改变已确认的产品能力；清理后确认没有无关平台耦合残留，再进入架构判断。

4. **判断仓库架构。** 检查清理后的文件树，识别实际存在的应用、可独立部署的服务和共享包。只要技术上可行且架构适用，就采用基于 pnpm workspace 的 monorepo；workspace 边界只覆盖真实存在的应用和包。如果有明确技术限制导致 monorepo 不适用，说明限制并推荐最简单兼容的架构，取得用户同意后再按该架构继续。

5. **补充项目指引。** 将以下原则追加到根目录 `AGENTS.md`；文件不存在时创建。保留原有指引，并避免重复添加：

   - 选择能够完全满足当前需求的最简单实现。避免预防性的抽象、额外配置和不必要的间接层。
   - 逐层构建系统。从能够端到端运行的最小版本开始，在已经可以正常工作的产品之上逐步增加新的能力。不要为了尚未完成的复杂设计，牺牲一个已经能够正常工作的产品。
   - 保持组件模块化，并明确分离不同关注点。
   - 如果成熟且维护良好的现有库能够降低整体复杂度或提高可靠性，优先使用它。没有明确理由，不要重新实现已有的通用功能。
   - 在自己实现功能或添加新的依赖包之前，优先利用项目中已经存在的依赖。不要在没有检查文档和类型定义之前，就假设某个库不具备所需能力。
   - 架构决策要面向长期。不要接受“先这样做，以后再替换”的临时方案。

6. **总结设计规范。** 根据清理后的 UI 源码、样式、资源文件和用户提供的截图，按照 [Google Labs DESIGN.md 格式](https://github.com/google-labs-code/design.md) 在项目根目录生成 `DESIGN.md`。记录有证据支持的颜色、字体、间距、布局、形状、组件状态和响应式行为。不要臆造品牌决策；无法确定的数值在正文中标为估算。使用 `npx --yes @google/design.md lint DESIGN.md` 校验，不把 CLI 加入项目依赖。

7. **用 Graphify 总结项目结构。** 按照 [Graphify 官方说明](https://github.com/Graphify-Labs/graphify) 操作。若 CLI 不存在，优先用 `uv tool install graphifyy` 安装隔离环境中的命令行工具，然后为当前仓库安装：`graphify install --project --platform codex`。使用 Codex skill 执行 `$graphify .`，保留有用的项目产物，包括 `graphify-out/GRAPH_REPORT.md` 和图文件。只有项目确实需要时才安装 Graphify 可选扩展。

8. **审计并补齐功能实现。** 不要因为 Gemini 模板可以启动或构建，就认为需求已经完成。只审计 Gemini 初稿对已确认产品功能的覆盖情况；以已确认需求为功能验收依据，不把 `DESIGN.md` 当作功能规格，本步骤也无需修改或校验 `DESIGN.md`。检查实际页面、交互、数据流、本地持久化、设备适配、错误处理和空状态；结合源码与运行结果，记录每项是已完成、部分完成、缺失还是行为不符，并附上对应文件或可复现行为作为依据。只处理已确认功能范围内的差距，不顺手添加新功能。

   基于审计结果制定一个可执行的实施计划，拆分任务并标明相关文件、依赖关系和适当的验证方式；有 `superpowers:writing-plans` 时使用该 skill，并将计划保存在项目计划目录。随后按计划逐项实现缺失或不完整的功能，不要停在审查报告或计划上。实现时沿用项目架构与现有依赖，并在每项完成后做与改动相称的检查；若有重要需求无法从已确认规格推断、或必须扩大产品范围才能继续，再向用户提问。全部实现后，重新逐项核对需求覆盖情况，运行项目适用的构建和检查，并执行 `graphify update .` 同步结构图。

完成后汇报架构选择、创建或修改的文件、需求审计与补全结果、校验结果，以及因工具缺失或项目资料不足而未完成的事项。没有实际执行 AI Studio 手动步骤、Graphify 或设计校验时，不要声称已经完成。
