# TodoTree 产品体验与整改建议

评审日期：2026-09-28  
评审版本：`e538357`（`main`）  
交付性质：基于需求访谈、实际界面体验和代码核对的整改建议，供后续开发使用。

评审方式调整：按用户最新要求，后续采用静态代码分析，不再继续浏览器交互。已有界面观察作为历史证据保留，未实测的部分以代码判断和待验收项呈现。

## 1. 产品要帮助用户完成什么

用户希望规划自己的执行计划。一个大目标最初只能拆出粗略步骤，执行过程中又会发现某个步骤需要继续细分，因此任务结构需要随思考和执行逐渐生长。

典型场景是完成一份 EDA 与 Data 可视化课程 Report：先拆出信息检索、寻找数据集、做实验，再把做实验拆成 EDA 和数据可视化，之后继续拆出可以直接执行的任务。

成功的体验应当是：用户想到下一步，就能在对应位置快速记下来；想到多个步骤，就能连续添加；拆分后能看清整个计划；切到列表，就能按优先级处理全部叶子任务。

### 本次访谈已确认的规则

| 事项 | 已确认结论 |
| --- | --- |
| Flow 的作用 | 展示和编辑父子任务关系，支持执行过程中继续拆分 |
| 列表内容 | 展示 Flow 中全部叶子任务，包含已完成和未完成项 |
| 前置依赖 | 第一版不根据前置任务是否完成，决定任务是否出现 |
| 第一版排序 | `重要程度 + 紧急程度` 的总分降序；两项各为 0–100，合计 0–200 |
| 后续排序 | 将来可以考虑配置，第一版先提供确定的默认规则 |
| 任务规模 | 通常最多几十个任务 |
| 完成规则 | 只有叶子可以标记完成；已完成叶子需要先取消完成，才能增加子项 |
| 删除规则 | 删除当前任务及全部后代；父任务失去最后一个子项后成为未完成叶子 |
| 数据 | 本地保存；无账号和服务器；JSON 手动导入导出、迁移设备 |
| 字段与标签 | 标题、备注、截止日期、重要程度、紧急程度、多个标签；标签支持名称和颜色 |
| 当前最主要的痛点 | Flow 中新建子项、连续新建多个子项、删除等操作不方便 |
| 移动端方向 | 如果 Flow 操作体验不好，可以隐藏 Flow。本次小屏体验支持采用这一方向 |

**本次新增的排序要求，是需要补上的产品要求；不能把它描述成原有明确规则的回归故障。** 本文提出的连续添加方式、批量输入、撤销、分支折叠等具体交互属于整改建议，并非用户已逐项确认的需求。

延续已有清爽效率工具的视觉风格。整改集中在操作路径、任务关系和反馈上。

## 4. Flow 核心交互建议

### 4.1 节点上能看见、能直接使用的操作

建议选中或悬停节点时，在节点旁显示轻量工具条。键盘聚焦也必须能显示相同操作。

| 操作 | 推荐入口 | 结果与约束 |
| --- | --- | --- |
| 添加子任务 | 节点右侧明确的“＋ 子任务” | 在该节点下创建子项；完成叶子不可用，并说明先取消完成 |
| 添加同级任务 | 工具条“同级” | 使用当前任务的父节点；根节点的同级仍是根任务 |
| 连续／批量添加 | 子任务输入区中的明确入口 | 创建目标父节点保持不变，不随着刚创建的任务改变 |
| 改标题 | 标题双击或工具条“改名” | 就地编辑标题；完整字段仍在详情中编辑 |
| 删除 | 工具条“更多 → 删除” | 明确显示目标与后代数量，确认后级联删除 |
| 查看详情 | 保留单击节点打开右侧详情 | 点击节点内操作按钮时，不额外触发整卡点击，也不抢走输入焦点 |

右键菜单可以复用这些操作，但不能成为唯一入口。不要让用户必须猜出右键或记住快捷键，才能完成基本任务。

保持父节点和叶子节点使用相同的卡片体系，用状态标识表达区别。先保留自动树布局；用户当前要求的直接操作，不需要以开放任意连线或任意拖动坐标为前提。

### 4.2 单次添加与连续添加

推荐把“想几个步骤、就记几个步骤”做成同一个短流程：

1. 点击 Report 的“＋ 子任务”，在节点附近打开小输入区。
2. 输入区明确显示“添加到：Report”，标题框立即获得焦点。
3. 输入“信息检索”，按 Enter 创建。
4. 输入框清空，仍然属于 Report，可以继续输入“寻找数据集”“做实验”。
5. 按 Esc 或点“结束添加”关闭输入区。

创建成功后显示新节点，但输入上下文继续留在原父任务。希望进一步拆分刚创建的任务时，再明确点击该任务的“＋ 子任务”。

验收重点：连续输入三个标题后，得到三个兄弟节点；不需要三次打开详情，也不需要反复重新寻找父节点。输入框中应有“Enter 添加，Esc 结束”的提示。

中文输入法正在选词时，Enter 只确认候选词。必须避免将输入法确认误当成提交，或者在编辑标题时触发全局新增、删除快捷键。

### 4.3 一次创建多个子任务

在相同的子任务入口里提供“批量输入”，采用一行一个标题的简单格式：

```text
信息检索
寻找数据集
做实验
```

确认前显示“将在 Report 下创建 3 个子任务”。去除每行首尾空白，忽略空行，保留输入顺序。每一行生成独立的稳定 ID；同名标题不自动合并。

批量确认应当是一次整体操作，统一保存并更新图表、列表；取消时不产生任何任务。第一版不解析缩进层级、不根据标点猜测父子关系。

单个和批量添加共享完成限制：已完成叶子必须先取消完成。限制应落实到共同的数据操作入口，覆盖鼠标、键盘、批量入口和移动端。

### 4.4 创建草稿与改名

新建时先收集标题，确认后再写入任务树。关闭空白输入或按 Esc 不留下“新建子待办”占位项；已有标题改名时取消则恢复原值。

有效标题至少包含一个非空白字符。备注、截止日期、评分和标签继续在详情中设置。就地编辑标题不应拖动画布，也不应把删除文字理解为删除任务。

### 4.5 删除与恢复

节点上的删除动作应直接打开确认，不要求先滚动详情面板。确认文案使用真实任务名称，例如：

> 删除「做实验」？将一并删除它的 2 个后代任务，共 3 项。

确认前展示范围；取消后保留选择和视口。删除父任务时删除整棵子树，不能把后代提升成根任务或接到其他节点。删除最后一个子项后，父任务按照已确认规则变成未完成叶子，并出现在列表中。

建议增加“已删除 3 项 · 撤销”。第一版可明确只支持当前会话最近一次结构操作的撤销，恢复任务原 ID、父子关系、原顺序、字段和完成状态。实际可恢复范围必须与提示一致，不能只恢复画布卡片而丢掉数据。

### 4.6 画布位置与侧栏

当前每次树结构变化都会重新执行全图适配。推荐调整为：

- 首次打开非空图、导入另一份完整计划、用户点击“查看全图”时，才主动适配全图。
- 新增、改名、完成、删除时保留当前缩放比例和用户所在区域。
- 新节点在屏幕之外时，只做让相关父子节点进入可见区域所需的最小平移；必要时给出“定位新任务”。
- 桌面详情面板占据真实布局宽度。画布的可用区域应扣除侧栏，选中节点和新增输入区不能被遮挡。
- 在 Flow 和列表间切换时保留 Flow 视口与选择；从列表发起“在图表中定位”才主动定位目标。
- 结构自动布局时尽量以正在编辑的父任务为锚点，避免为了新建一个子项而让整个工作区域移动。

增删节点后的布局可以改变，但不应把“重新布局”与“重置用户视口”绑定成同一个动作。

### 4.7 完成状态与分支浏览

叶子任务在图上明确显示未完成／已完成状态，使用文字或勾选标识配合颜色。卡片仍保持一致的结构。父任务显示子项数量；如显示进度，应写成“已完成叶子 1 / 3”，不能把父任务变成可手动勾选的完成任务。

建议后续补充分支折叠，帮助用户只看正在拆分的部分。折叠仅改变图表展示：被折叠的后代仍然存在，父任务仍然不是叶子，全部真实叶子仍然出现在列表中。不要用“当前没有显示子节点”判断一个任务能否完成。

## 5. 列表需要实现的执行逻辑

### 5.1 排序的唯一默认规则

```text
优先级分数 = importance + urgency
默认顺序 = 优先级分数从高到低
```

全部叶子统一参与排序。已完成项保持可见，也不因完成状态被自动移动到最下方。总分相同，建议暂时保持稳定的树遍历顺序，避免刷新或编辑无关字段后跳动；这一同分规则是实现建议。

本次示例的正确顺序应为：

| 顺序 | 任务 | 总分 | 状态 |
| --- | --- | --- | --- |
| 1 | Data 可视化 | 190 | 已完成 |
| 2 | 寻找数据集 | 170 | 未完成 |
| 3 | EDA | 0 | 未完成 |

在列表顶部明确标注“按重要＋紧急排序”，条目显示总分，同时能看到组成分数。不要让用户自己在每一行心算两项之和。

排序只影响执行列表，不改变 Flow 中的兄弟顺序或保存的任务树。更新评分后更新列表；编辑输入中的暂态值应有一致的处理方式，避免用户尚未输入完，任务就跳走。

### 5.2 列表与计划树的衔接

保留已有的祖先路径，并让路径中的父任务可以打开。桌面增加“在图表中定位”，直接跳到任务附近，避免用户面对全图重新找位置。

从叶子详情继续拆分后，原任务变成父任务并从列表移除，新子项进入列表。完成创建后应明确提示这一变化，并让用户仍能返回刚才的父任务继续添加同级子项。

列表应能直接勾选完成；任务标题也应有可用键盘打开详情的入口。完成开关和打开详情应使用独立的点击区域。

## 6. 移动端建议

本次 390px 宽度的六节点体验，已足以支持第一版隐藏小屏 Flow。建议沿用现有 768px 布局分界：小于该宽度时仅展示列表和设置；横屏平板等宽屏设备再单独验证是否开放 Flow。分界值属于建议，不是已经完成的真机结论。

**隐藏 Flow 与补齐父子导航必须一起交付。** 仅删除顶部“图表”按钮，会让用户失去管理父任务的主要入口。

移动端最小可用流程：

1. 列表仍显示全部叶子，并按总分排序。
2. 点开任务，顶部显示可点击的祖先路径和“返回上一级”。
3. 父任务详情显示直接子任务清单，允许进入、继续添加子项和删除。
4. 完成一次拆分后，能回到该父任务继续添加其他子项；不必通过 Flow 找回位置。
5. 完成开关、关闭详情、添加与删除入口具有足够的触控区域；建议有效点击区域至少 44 × 44px。
6. 软键盘打开后，标题、提交动作和错误提示仍可见；提交后不自动失去当前任务位置。

若用户正在桌面 Flow 中缩窄窗口，应用应切换至列表或当前任务详情，保留选中的任务，不出现空白页，也不删除任何图表数据。

## 7. 数据与日常使用可靠性

### 7.1 本地恢复风险

代码显示：读取本地数据失败时，应用使用空数据并提示“原始数据已保留”；后续编辑仍会向同一个存储键写入。这意味着用户在错误提示下新建一个任务，就可能覆盖那份尚待恢复的原始数据。

这是代码核对发现的条件性风险，本次没有通过破坏存储进行复现。建议加载失败后进入明确的恢复状态：可下载原始内容、选择备份恢复，或明确确认开始新数据后再解除写保护。不能只依靠一条提示保证恢复机会。

保存失败时，保留内存中的任务并提供导出入口，允许重试；保存成功和写入失败的提示应与真实结果一致。

### 7.2 需要保留并补测的现有能力

已有标签管理、JSON 导入导出、导入前校验和整体替换确认。下一轮应保留这些能力并补测实际闭环，不应把已经存在的界面误写成“缺少导入导出”。

验收应覆盖：导出再导入后整棵树和标签一致；非法文件和取消导入不改变原数据；删除标签后任务引用同步清理；保存失败时仍能导出当前内存内容。JSON 中父任务的 `completed` 字段约定也需要统一文档与实现，当前实现要求所有节点均有布尔值，父节点为 `false`。

### 7.3 暂不直接决定的规则

目前新增子任务的两个分数均为 0。未来按总分排序后，拆分一个高分任务会让它的子任务落到后面。

建议在实施前确认是否采用“创建时复制父任务评分，之后独立编辑”。这是一项待决定的产品规则；不应无声改变默认值，也不应预先引入父子评分持续联动。

## 8. 建议的实施顺序

### 第一批：打通桌面拆分与执行流程

交付 F01、F02、F03、L01，同时完成与新入口直接相关的标题草稿、完成限制和删除确认。

可交付结果：用户能够围绕 Report 节点连续添加三个子任务，再进一步拆分“做实验”；无需反复切换详情和重找父节点；画布保持稳定；列表立即按总分呈现全部叶子。

先完成鼠标可发现的入口、正确的数据更新和反馈，再增加快捷键。创建、批量创建、删除都需要使用统一的任务树操作，避免多个入口行为不一致。

### 第二批：达到稳定的日常使用体验

交付 Flow 完成状态、删除撤销、视图定位、父子任务导航、移动端隐藏 Flow、分支折叠、本地数据恢复与键盘／触控完善。

其中 N01 和 M01 应成组完成，不能先隐藏 Flow 再留下父任务访问缺口。用 30–50 节点的实际案例和真机验证这一批的效果。

### 后续再安排

- 可配置的排序规则：已有用户意向，待第一版默认排序稳定后展开。
- 子任务评分继承：先确定产品规则。
- 移动任务到另一父任务：针对真实使用频率再设计；如做，需要防止移入自身或后代，并保留整棵子树。

当前首批不需要账号、自动同步、任务依赖系统、自由连线、复杂排序配置面板或任意坐标布局。用户已有的本地工作方式与几十任务的规模，足以指导这轮整改。

## 10. 实现定位与约束

下面的定位用于减少实施时重新摸索代码的成本。优先复用现有 React Flow、树布局和任务树数据模型。

| 位置 | 当前行为 | 对应工作 |
| --- | --- | --- |
| [TodoNode.tsx](../../apps/web/src/components/TodoNode.tsx:10) | 节点卡片只打开详情，未呈现完成状态 | 节点操作入口、就地编辑、状态反馈 |

| [ConfirmModal.tsx](../../apps/web/src/components/ConfirmModal.tsx:31) | 已有取消按钮初始焦点和关闭后返回，缺少完整焦点约束 | 保留已有行为，补齐模态焦点管理 |

本地已安装的 React Flow 类型声明包含节点右键事件和删除前置事件。库能够承载这些入口，但业务操作仍需要同步任务树。仅让 React Flow 从屏幕删除一个节点，不能等同于完成应用的级联删除。

开发时应特别保持以下一致性：

- JSON 任务树继续作为唯一业务数据来源；列表、图节点、连线、统计都从它派生。
- 所有创建入口统一检查完成限制；所有删除入口统一执行级联规则。
- 列表排序、节点选择、视口与折叠状态不能意外改写任务层级或完成状态。
- 批量操作作为一次提交更新数据，避免出现部分创建成功、部分未保存的中间结果。
- 新交互复用现有依赖，不为本轮需求引入第二套图引擎、服务端或配置系统。

本轮建议完成后的衡量标准是：用户能顺着自己的思路，连续建立和调整一棵几十节点的计划树，并在列表中直接看到全部叶子任务的优先级顺序。
